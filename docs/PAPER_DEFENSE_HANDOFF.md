## 3. The 5 custom-written functions — full defense detail

Every other statistical function in the codebase (`binomial_test`,
`fisher_exact_test`, `welch_t_test`, `pearson_correlation`,
`spearman_correlation`) is a direct, unmodified `scipy.stats` call — no
design defense needed beyond "we called the library function correctly."
These 5 contain genuine hand-written arithmetic or a hand-rolled resampling
loop. Full line-by-line verification and worked examples are in
`docs/MATH_CORRECTNESS_AND_COMPREHENSION.md`; provenance (is any of this
copied from somewhere?) is in `docs/PROVENANCE_VERDICT.md`. Both docs were
read in full for this handoff — content below is drawn directly from them,
not re-derived.

### 3.1 `bootstrap_resample()` / `run_bootstrap_ci()` — `research_analysis.py:2877`, `:3167`

**What it does:** Efron's (1979/81) percentile bootstrap — draw B resamples
of size n *with replacement* from the real trade returns, compute each
resample's sum/mean, take the 2.5th/97.5th percentiles of the resulting
distribution as the 95% CI.

**Why designed that way:** 27 trades is too few and too right-skewed (a few
large winners) to safely assume a normal-theory CI (mean ± 1.96·SE) is
valid. The bootstrap makes no distributional assumption — it uses the data's
own actual shape. Resampling *with* replacement (not a permutation) is what
lets the resample's total vary at all; resampling at the *original* sample
size (not larger/smaller) matches Efron's prescription so resample-to-resample
variability reflects genuine sampling uncertainty, not a size artifact.

**Paper must state:** this is the source of the "must not silently unify"
rule with the JS B=2,000 cross-check (§6) — the paper should say so plainly,
not just show two numbers.

### 3.2 `bootstrap_ablation_arm_vs_baseline()` — `research_analysis.py:2621`

**What it does:** a between-arm empirical bootstrap p-value. Resamples an
ablation arm's trade pool **at the baseline's sample size (27), not the
arm's own size (140/138)**, and reports what fraction of those 27-sized
resamples meet or beat the baseline's actual win rate / avg return.

**Why designed that way:** resampling at 27 answers "if I drew a
baseline-sized sample from this weaker population, how often would it look
this good?" — the actual question being asked. Resampling at 140 would
instead measure uncertainty in the arm's own mean, a different question
entirely. `>=` (not `>`) is used so ties count as "beating" — the standard
"at least as extreme" convention for an empirical p-value.

**Defense note:** see §2.7 — the value this function currently produces
against the *reconstructed* trade pool (p=0.009, 0.0135) does **not** match
the value the paper cites (p=0.0020), because the reconstruction's per-trade
outcomes diverge from the paper's original (uncommitted) run. The function
itself is not in question; which trade pool it's fed is.

### 3.3 `mde_power_analysis()` — `research_analysis.py:2989`

**What it does:** standard two-sample normal-approximation Minimum Detectable
Effect: `MDE = (z_α/2 + z_β) × sqrt(sd_true²/n_true + sd_false²/n_false)`,
using `scipy.stats.norm.ppf` only for the two z-quantiles — the combination
formula itself is hand-written arithmetic.

**Why designed that way:** reframes a "not significant" per-criterion result
as "this sample size (n=4..23 per criterion) is underpowered to detect an
effect of the size actually observed" — a different, more honest claim than
"no effect exists." A normal approximation (not Welch's t) is used
deliberately: MDE is about a *hypothetical future* sample, so it can't
condition on a data-dependent Welch-Satterthwaite df in advance; this is
standard practice for a post-hoc power sanity check.

**Flag — F2, state in the paper:** `detectable` reads Python `False` (not
"undefined") when a subgroup's SD is NaN (n<2), because any comparison
against NaN is `False` in Python. **Does not occur on real data** — all 5
criteria have n=4..23, never <2 — but if a panelist asks "what happens with
a 1-trade subgroup," the honest answer is "the code would silently say
`False`, which is misleading; it should say 'undefined.'" This should be one
sentence in the paper's limitations, not left for cross-examination to
surface.

### 3.4 `max_drawdown_pct()` — `research_analysis.py:3044`

**What it does:** the standard 3-line quant-finance formula — running peak
(`.cummax()`), percent decline from that peak at every point, take the
single worst (most negative) value across the whole equity curve.

**Why designed that way:** percentage (not dollar) drawdown lets the
strategy, DCA, and lump-sum arms be compared directly despite very different
equity-curve shapes from the same $10,000 start (§2.6). Tracking the
*running* max (not just final-value-vs-peak) is what catches a mid-history
dip that later recovers — e.g. the strategy's −6.46% MaxDD happened
mid-window and does not show up if you only compare the final value to the
all-time high.

### 3.5 `sharpe_sortino_ratios()` — `research_analysis.py:3068`

**What it does:** Sharpe (1966/94) and Sortino & van der Meer (1991), both
annualized via `× sqrt(periods_per_year)`. Sortino's downside deviation is
`sqrt(mean(min(R,0)²))` computed over **all** N periods (not just the
losing ones).

**Why designed that way:** the full-N Sortino denominator is the
textbook-correct convention per the original 1991 paper — verified by
directly checking against a popular public tutorial (codearmo.com) that
instead divides by the count of losers only; this codebase deliberately does
**not** match that non-standard shortcut.

**Flag — F1, the most important one to state in the paper unprompted:**
Sharpe/Sortino both implicitly assume risk-free rate (and Minimum Acceptable
Return) = 0 — the code uses raw per-bar returns directly rather than
subtracting a risk-free benchmark first. Defensible for a crypto strategy
with no explicit funding-rate leg modeled, but it's a real, nameable
deviation from Sharpe's general `SR = E[R_a − R_f]/σ` formula, and it is
**not currently stated anywhere in the paper or in the code's docstring.**
If asked "where's the risk-free rate," the honest answer is "assumed zero,
not subtracted, not documented — but mathematically implied by using raw
returns directly." This should be a disclosed assumption in the Methodology
section, not a gotcha the panel finds first.

**Flag — F3, plain percentile bootstrap, applies to §3.1 too:** not
bias-corrected (BCa) — standard, disclosed-as-standard simplification, but
know the term "BCa" by name if asked why a corrected variant wasn't used.

### 3.6 AI-assistance disclosure — say this unprompted, not just for these 5

Per `PROVENANCE_VERDICT.md`: none of these 5 functions (nor the 5 direct
`scipy.stats` wrappers) were copied from any specific paper's or
repository's implementation — each independently implements a standard
formula from public documentation. But every commit introducing or
materially editing them carries a `Co-Authored-By: Claude Sonnet 5` trailer.
The accurate answer to "did you personally write this" is: *directed the
design (which test, which populations, which parameters), drafted with AI
assistance rather than typed unaided, then verified against known-good
regression fixtures* — distinct from both "wrote it alone" and "copied a
paper's code." State it in those terms rather than let the panel assume
either extreme.

## 5. Data provenance summary

- **Source:** Binance `get_klines` REST endpoint, `BTCUSDT` symbol, 4-hour
  interval, paginated in batches of 1,000 candles.
- **Timestamp convention:** raw millisecond `open_time` shifted by a fixed
  **+8 hours** — the stored dataset's `open_time` is UTC+8, not raw UTC.
  Must be stated explicitly anywhere the paper reproduces a specific bar's
  timestamp.
- **Window:** 2022-01-01 08:00:00 through 2026-01-01 08:00:00.
- **Bar count — the exact arithmetic (defensible if a panelist checks it
  live):** 2022-01-01 to 2026-01-01 spans exactly 1,461 calendar days (365 +
  365 + 366 + 365, the 366 accounting for the 2024 leap day). At 6 four-hour
  bars/day, that's 1,461 × 6 = 8,766 bar-*intervals*; because the final bar
  is itself included as a row (not used only as an exclusive upper bound),
  the row count is 8,766 + 1 = **8,767**. The paper's original figure of
  8,760 was a plain arithmetic slip, corrected in both code and the paper.
- **Gap check:** the set of unique inter-bar timestamp deltas across all
  8,767 rows is the single value 4 hours — no gaps.
- **Live reconfirmation this pass:** `artifacts/paper_sync_report.md`
  (generated 2026-08-20T14:54:01, still current — no commits since) shows
