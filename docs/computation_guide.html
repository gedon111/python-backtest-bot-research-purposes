§ 1

The machine, end to end

One file does everything. research_analysis.py is the backtest engine, the statistics pipeline, the database layer, and the dashboard's HTTP server — one process, no imports between stages.

Nothing in this project is fitted. A fixed set of rules walks forward through 8,767 candles one bar at a time, records 27 trades, and every published statistic is a function of that one trade log. The whole system is a straight line:

load_candles()
artifacts/candles.csv → 8,767 rows of OHLCV. Read from disk, never the network.
compute_indicators()
Adds MACD, MACD_signal, MACD_hist, RSV, K, D, J, ATR, ATR_200 as nine new columns. Pure column math, no loops.
compute_smc()
Scans for market structure and returns 761 Order Block dicts, each scored on five true/false quality criteria.
simulate_trades()
The bar loop. Starts at bar 55, evaluates the entry gate when flat and the exit ladder when in a position. Produces the 27-trade log.
Sections 5 & 5B
Six statistics plus the applied analyses (cost sensitivity, DCA head-to-head, regime split) — all computed from the trade log alone.
Plain language — what "the trade log alone" means

Once the simulation finishes, the price data is done doing work. What remains is a table of 27 rows: side, entry bar, exit bar, entry price, exit price, percentage return, bars held, exit reason. Every headline statistic in the paper is arithmetic on that table.

The win rate counts how many of the 27 pnl_pct values are above zero. The total return adds all 27 together. The bootstrap draws 27 values from that column at random ten thousand times. The correlation compares two of its columns. This is why the paper can be checked by hand — and why the appendix prints all 27 rows.

Why this matters at a defense

If a panelist asks "how do we know SciPy gave you the right answer," the answer is not "SciPy is trusted." It is that a spreadsheet formula and an independent TypeScript file arrive at the same figures from the same raw rows. The one place the surfaces visibly disagree — the bootstrap interval — was traced to its cause and is reported as two numbers rather than merged into one. That disagreement is evidence the cross-check is real.

§ 2

The data

One frozen CSV. Everything downstream is deterministic from it.

Rows8,7674-hour candles
First bar2022-01-0108:00 (UTC+8)
Last bar2026-01-0108:00 (UTC+8)
Gaps0all deltas = 4h

Why 8,767 and not 8,760

2022-01-01 to 2026-01-01 is exactly 1,461 calendar days — 365 + 365 + 366 (2024 is a leap year) + 365. At six 4-hour bars per day that is 1,461 × 6 = 8,766 intervals. The final bar at 2026-01-01 08:00 is included as a row rather than used as an exclusive upper bound, giving 8,766 + 1 = 8,767.

An earlier draft cited 8,760, a plain 365 × 24 arithmetic figure that dropped both the leap day and the endpoint bar. That was corrected; the manifest, the loader, and the paper all now agree on 8,767.

The timestamp convention

Binance returns open_time in milliseconds UTC. get_candles() converts it and adds a fixed +8 hours. Every timestamp in candles.csv, in the trade log, and in the paper is therefore UTC+8, not raw UTC. This shifts labels only — it does not reorder bars or change any computed value.

The second window

load_formulation_period_window() reads artifacts/candles_extended.json and returns the 2018-01-01 08:00 → 2022-01-01 04:00 window, 8,750 rows. This is the period the strategy's rules were formed against by visual inspection, so it is not out-of-sample. It ends one bar short of the main window's first bar so the two never overlap.

Plain language — why the formulation window is reported at all

Rules that were invented by looking at a chart usually look best on that same chart. That is the classic overfitting signature, and it is what a skeptical reader will suspect first.

So the study reports the formulation window on purpose, as a self-incrimination test. The strategy scores 60.00% and +21.82% there, against 70.37% and +30.31% on the reported window. It does worse on the data it was built from. That is the opposite of what curve-fitting produces, and it is the single strongest piece of evidence in the paper that the rules were not tuned.

MACD (12, 26, 9)

research_analysis.py · Section 3

# --- MACD (12, 26, 9) ---
ema_fast = df["close"].ewm(span=12, adjust=False).mean()
ema_slow = df["close"].ewm(span=26, adjust=False).mean()
df["MACD"]        = ema_fast - ema_slow
df["MACD_signal"] = df["MACD"].ewm(span=9, adjust=False).mean()
df["MACD_hist"]   = df["MACD"] - df["MACD_signal"]
Expanded — pandas span n means alpha = 2/(n+1)
EMA₁₂(t) = C(t)·(2/13) + EMA₁₂(t−1)·(11/13)
EMA₂₆(t) = C(t)·(2/27) + EMA₂₆(t−1)·(25/27)
MACD(t) = EMA₁₂(t) − EMA₂₆(t)
Signal(t) = MACD(t)·(2/10) + Signal(t−1)·(8/10)
Hist(t) = MACD(t) − Signal(t)

adjust=False is the load-bearing argument. It selects the pure recursive form above — each value depends only on the current close and the previous EMA. The alternative, adjust=True, rescales early values using the full window and would make the series depend on where the data happens to start.

Only MACD_hist is read by the strategy. The MACD and MACD_signal columns are exported for the dashboard and the diagnostic touch log, but no entry or exit condition references them.

Plain language — reading the histogram

An exponential moving average is a running average that weights recent candles more heavily. MACD subtracts a slow one from a fast one: when the fast average pulls above the slow one, recent prices are outrunning older prices, and momentum is upward.

The histogram goes one level further — it is the gap between the MACD line and its own smoothed version. What matters to this strategy is not whether the histogram is positive, but which way it is moving. A histogram that is below zero but rising means the sellers are still in control but losing grip. That is the moment the long entry is looking for: not a reversal that has already happened, but one that is starting.

KDJ (9, 3, 3) — the fixed entry series

# --- KDJ -- EWM alpha = 1/3, matching the standard KDJ smoothing ---
period = int(kdj_period)                                  # 9
rolling_low_min  = df["low"].rolling(period, min_periods=1).min()
rolling_high_max = df["high"].rolling(period, min_periods=1).max()
rsv_denominator  = (rolling_high_max - rolling_low_min).replace(0, np.nan)
raw_stochastic_value = ((df["close"] - rolling_low_min) / rsv_denominator * 100).fillna(50)

kdj_smoothing_alpha = 1.0 / 3.0
df["K"] = raw_stochastic_value.ewm(alpha=kdj_smoothing_alpha, adjust=False).mean()
df["D"] = df["K"].ewm(alpha=kdj_smoothing_alpha, adjust=False).mean()
df["J"] = 3 * df["K"] - 2 * df["D"]
Formula
RSV(t) = 100 · [ C(t) − min(L over last 9) ] / [ max(H over last 9) − min(L over last 9) ]
K(t) = ⅔·K(t−1) + ⅓·RSV(t)
D(t) = ⅔·D(t−1) + ⅓·K(t)
J(t) = 3·K(t) − 2·D(t)

Two edge-case details that the formula alone does not show, both in the code above:

  • min_periods=1 — the rolling window produces a value from the very first bar rather than nine NaNs. The first bars use a shorter effective window.
  • .replace(0, np.nan) then .fillna(50) — if a 9-bar window has an identical high and low (a completely flat stretch), the RSV denominator would be zero. That bar's RSV is set to the neutral 50 rather than producing a division error.
The most misunderstood part of this strategy

There are two KDJ systems in this codebase, and they never share state. This one — the fixed 9-period series computed once over the whole dataset — is the only one the entry conditions ever read. A second, adaptive KDJ exists solely to time one exit signal after a trade is already open; it is described in §6. Confusing the two is the single most common misreading of the design.

ATR (14) and ATR (200)

previous_close = df["close"].shift(1)
true_range = pd.concat([
    df["high"] - df["low"],
    (df["high"] - previous_close).abs(),
    (df["low"]  - previous_close).abs(),
], axis=1).max(axis=1)

df["ATR"]     = true_range.rolling(atr_period, min_periods=1).mean()   # 14
df["ATR_200"] = true_range.rolling(200, min_periods=1).mean()
Formula
TR(t) = max( H(t) − L(t), |H(t) − C(t−1)|, |L(t) − C(t−1)| )
ATR₁₄(t) = (1/14) · Σ TR(t−i), i = 0…13
ATR₂₀₀(t) = (1/200) · Σ TR(t−i), i = 0…199
Known stale comment — already disclosed in the paper

The comment directly above this code in research_analysis.py says "Wilder's smoothing (RMA)… equivalent to ewm(alpha=1/n, adjust=False)." The executed code is a plain rolling arithmetic mean, not Wilder's smoothing. The two produce different numbers.

The paper is correct and already states this explicitly: "Both ATR windows are computed as a simple rolling mean rather than Wilder's original exponential smoothing, despite an inherited code comment suggesting otherwise." The rolling mean is the deliberate choice — an orphaned Binance backtest bot (Wilder ATR backup).py confirms the exponential version was the one abandoned. Only the comment is wrong, and correcting a comment changes no number. It is listed again in §11 because it is exactly the kind of thing a panelist reading source will spot.

ATR₁₄ sizes risk: stop-loss distance, the minimum-stop filter, the ATR-move exit, and the breakeven ratchet all multiply it. ATR₂₀₀ is the long-run volatility baseline: it forms the regime ratio used as an entry filter, and it is the yardstick for two of the five Order Block quality criteria.

Plain language — why true range, not just high minus low

The obvious way to measure a candle's size is high minus low. That undercounts gaps. If Bitcoin closes at $40,000 and the next candle opens and trades entirely between $42,000 and $42,500, its high-minus-low is only $500 — but price actually moved $2,500.

True range fixes this by taking the largest of three spans: the candle's own range, and the distance from the previous close to this candle's high and low. Averaging true range over 14 candles gives ATR — a plain-language answer to "how far does this market typically travel in one candle right now."

That number is what makes the stop-loss adaptive. A fixed 2% stop is too tight in a violent market and too loose in a quiet one. A stop placed a multiple of ATR away is the same amount of market noise away in both.

Order Blocks — where the large participants already acted

MACD and KDJ say when. Order Blocks say where. The strategy will not take a momentum signal that occurs at an arbitrary price — it only acts when price has returned to a zone where a decisive move previously originated.

Detected761order blocks
Supply383sell-side zones
Demand378buy-side zones
Internal6595-bar pivots

How a block is found

Two independent structural passes run over the same series, differing only in pivot lookback: INTERNAL_STRUCTURE_LOOKBACK_BARS = 5 and SWING_STRUCTURE_LOOKBACK_BARS = 50. In each pass:

  1. A candle at index pb = i − size is confirmed as a pivot high only by strict right-side comparison: H[pb] > max(H[pb+1 … i]). Mirror condition for a pivot low. No candle after i is read.
  2. When price later closes across a tracked pivot level, a break of structure (BOS) or change of character (CHoCH) is flagged.
  3. The Order Block is built from the price segment between the pivot candle and the crossover candle.

Two indices are kept deliberately distinct, and confusing them is how lookahead bugs get in:

  • ob_bar — the candle holding the block's own extreme. This is what the KDJ exit window measures back to.
  • created_at — the candle on which the breakout closes. The block does not exist to the simulator until after this bar.

A block is eligible for entry only while created_at < i < mitigated_at and i − created_at ≤ 500. It dies at 500 candles of age, or the moment price closes back through its boundary.

The five quality criteria

Each block is scored on five independently evaluated booleans. Their sum, 0 to 5, is stored as quality.

The quality score gates nothing in the headline result

The published baseline runs at min_ob_quality = 0, so no block is excluded by score. All five criteria are diagnostic in the reported result — they are recorded per trade and exported, but they filter nothing.

Two consequences worth knowing before a Q&A. First, the composite score across the 761 blocks runs 0–5 (93 / 154 / 206 / 197 / 90 / 21), but among the 27 blocks that actually triggered a trade the maximum is 4 — none of the 21 perfect-scoring blocks ever produced an entry. Second, the module constant DEFAULT_MIN_OB_QUALITY is 1, not 0. Calling simulate_trades() without an explicit threshold gives the 25-trade set, which is also what artifacts/trades_default_view.csv holds. The paper's 27 trades require min_ob_quality=0 passed explicitly.

The lookahead correction

This is the disclosed engine bug. The forward-search loops for Displacement and Fair Value Gap were originally bounded by the length of the whole dataset instead of by each block's own confirmation candle — so they could read one to two candles that would not have been available when the block became tradeable. Genuine data leakage.

Fixed by freezing every forward-search window at the confirmation bar, with runtime assertions left at each read site so a regression fails immediately rather than waiting for another audit. The 27-trade baseline is unchanged by the fix, because that baseline runs at threshold 0 and is unaffected by quality filtering.

Plain language — why a one-candle leak is fatal

A backtest's only claim to meaning is that it made each decision using only what was knowable at that moment. If a rule reads even one candle into the future, the backtest is no longer simulating trading — it is measuring how well a rule performs when it can see the answer.

The leak here was small and confined to two quality scores, and the reported result does not use those scores. That does not make it harmless. It makes it exactly the kind of defect that is invisible in the output and has to be caught by reading the loop bounds, which is what the no-lookahead audit did.

§ 5

The entry gate

_try_enter_long() and _try_enter_short(), Section 3. Evaluated at every bar the simulator is flat, against every currently-active block in turn. The first block passing all filters takes the trade.

The bar loop starts at index 55 (SWING_STRUCTURE_LOOKBACK_BARS + 5), so the 50-bar pivot structure has room to form. At each bar the loop reads the current and two previous values of MACD_hist and K, and derives two quantities:

Derived per bar
k_accel = (K(t) − K(t−1)) − (K(t−1) − K(t−2)) ← second difference of K
atr_r = ATR₁₄(t) / ATR₂₀₀(t) ← volatility regime ratio

Long entry — the full chain

Every condition must hold at the same candle close. A failure at any step moves to the next block; if no block passes, no trade opens on that bar.

  1. low <= ob["top"] and close >= ob["bottom"]
    Price is touching the zone. The candle must actually reach into the demand block. This is the "where" condition — everything after it is the "when".
  2. macd_hist < 0 and macd_hist > macd_hist_prev
    Momentum is negative but turning up. Buying into a zone while the histogram is still falling means catching the move too early; buying once it is already positive means catching it too late.
  3. macd_hist_prev > macd_hist_two_bars_ago
    Rising for at least two bars. One rising bar is noise. Requiring two consecutive rises makes the turn a trend rather than a flicker.
  4. K < 50.0 and K > K_prev and J < 60.0
    Oscillator is low and lifting. K < 50 and J < 60 confirm the pullback is genuinely oversold rather than a pause mid-rally; K > K_prev confirms it has started to recover.
  5. 1 <= k_accel <= 6
    K is accelerating, but not spiking. At or below 0, K is not yet accelerating in the trade's favour. Above 6, a single-bar spike — which, per the code comment, "tends to reset immediately" and is treated as noise.
  6. not (0.8 <= atr_r <= 1.0)
    Skip the dead zone. When short-term volatility sits just below its long-run baseline, the market is neither trending nor genuinely quiet. Entries are filtered out of that band entirely.
  7. stop_loss = ob["bottom"] − ATR₁₄ × 0.5 ; risk = close − stop_loss ; risk > 0
    Place the stop below the zone, with an ATR buffer. Half an ATR below the block's floor, so ordinary noise around the zone edge does not trigger it.
  8. risk / close >= 0.015
    The stop must be at least 1.5% away. Verbatim from the code: thin blocks "sit inside normal 4H noise and get stopped before the move even starts." A block too thin to clear this is rejected outright rather than traded with a tight stop.
  9. tp = get_structural_tp(...) or close + risk × 2.0
    Target real structure when it exists. get_structural_tp() returns the nearest opposing block above price — the lowest bottom among active supply blocks. If there is none, fall back to twice the risk distance.
  10. (tp − close) / risk >= 1.5
    Minimum 1.5 : 1 reward-to-risk. The last gate. A structural target sitting too close to entry fails here and the trade is skipped, even though every momentum condition passed.

Short entries mirror this exactly, against supply blocks, with the histogram positive and falling, K > 70.0, J <= 100.0, the stop at ob["top"] + ATR₁₄ × 0.5, and the structural target being the highest top among active demand blocks below price.

Plain language — what the whole chain is doing

Read the ten filters as one sentence: price has come back to a zone where a big move once started; selling pressure there is measurably fading rather than merely paused; the market is not in its indecisive volatility band; and the trade that results is far enough from its stop to survive normal noise while still offering at least one and a half times that risk in reward.

Each condition on its own is weak — thousands of candles satisfy any one of them. The point of the confluence is the intersection. Across 8,767 candles, all ten held simultaneously on only 27 occasions.

That is also the study's central weakness, stated plainly: a rule this restrictive produces a sample too small for strong statistical claims, which is precisely why the paper reports a wide bootstrap interval and refuses to claim more than the 27 trades support.

§ 6

The exit ladder

_check_long_exit_conditions() and its short mirror, Section 3. Evaluated every bar while a position is open, in a fixed priority order. The first condition satisfied closes the trade; the rest are not evaluated on that bar.

  1. peak_pnl >= 1.5 and close <= entry × (1 + peak_pnl × 0.5 / 100)
    Trailing 50% retrace. Once a trade has been up 1.5% at any point, it closes if it gives back half of its best unrealized gain. Arms only after the 1.5% threshold, so a trade is never trailed out before it has done anything.
  2. (i − entry_idx) >= 3 and kdj_reset_exit(state, "LONG")
    KDJ-reset exit. The adaptive exit oscillator has crossed back against the trade. Suppressed for the first three bars — per the code, single-bar KDJ fluctuations in bars 1–2 should not close a position.
  3. close >= entry + entry_atr × 1.8
    ATR-move exit. The trade has travelled 1.8 × the ATR measured at entry. A volatility-scaled profit target: the same amount of market movement in every regime.
  4. close >= entry + entry_atr × 2.0 → stop_loss = max(stop_loss, entry)
    Breakeven ratchet. Not an exit — it moves the stop up to entry, making the trade risk-free from that point. Note it sits below the 1.8 × ATR exit in priority, so a trade that reaches 2.0 × ATR has already exited at 1.8 × on an earlier bar.
  5. close <= stop_loss → "HIT STOP LOSS"
    Hard stop. Evaluated on the close, not intrabar. P&L is recomputed from the actual close rather than assuming a fill at the stop price.
  6. close >= take_profit → "HIT TAKE PROFIT"
    Hard target. The structural or 2× -risk target set at entry. In the 27-trade baseline this fires zero times — the ATR and trailing exits always arrive first.
One ordering detail that changes results if moved

The adaptive KDJ state is advanced with this bar's price action — kdj_reset_update() — after the trailing-exit check but before the KDJ-reset check. So on a bar where the trailing exit fires, the KDJ state is never advanced at all. Reordering these two lines changes which bar's data the exit signal is allowed to react to, and therefore changes the trade log.

Plain language — why the exit window is tied to the Order Block

The window length w is the number of candles between the block that triggered the trade and the entry itself. A block that formed 400 candles ago produced a trade on a slow structural timeframe; a block that formed 14 candles ago produced a fast one.

Setting the exit oscillator's window to that same distance means the exit is measured on the same timeframe as the setup. A slow trade gets a slow exit signal; a fast trade gets a fast one. The alternative — one fixed exit period for every trade — would apply a fast trade's sensitivity to a slow trade and close it on noise.

The entry side deliberately does not do this. It stays on a fixed 9-period series so that the decision to enter is measured identically for every trade, which is what makes the 27 entries comparable to one another.

Trade log conventions

Four definitions that every downstream statistic inherits. Getting these wrong is how two correct implementations produce different numbers.

Summed versus compounded — the reconciliation to state out loud

The headline +30.31% is the arithmetic sum of the 27 trade returns. The dollar figure $13,417.77 is those same 27 returns compounded in sequence from $10,000, which is +34.18%.

Both are correct; they are different quantities. The code makes this explicit rather than reconciling it — _run_strategy_dollar_arm() carries the comment that final_capital "is the REAL final value of the compounded, sequential equity curve — NOT back-derived from total_return_pct." The passive arms hold one position throughout, so no such gap arises for them.

The strategy equity curve

Because simulate_trades() never holds overlapping positions, the equity curve can be built by a simple sequential walk over exit bars — exact, not an approximation:

equity[0] = starting_capital
running_equity = starting_capital
for i in range(1, n_bars):
    if i in exit_pnl_by_bar:                      # a trade closed on this bar
        running_equity *= (1 + exit_pnl_by_bar[i] / 100)
    equity[i] = running_equity                    # flat between trades

The curve is a staircase: flat everywhere, stepping only at the 27 exit bars. Sharpe, Sortino and max drawdown are all computed from this series' bar-to-bar percentage changes — which is why the strategy's drawdown is shallow. It is out of the market 97.37% of the time and cannot draw down while flat.

1 · Exact binomial test

binomial_test(win_count, trade_count, null_win_probability=0.5)

If trades were coin flips with a 50% win probability, how surprising is 19 wins out of 27?

The computation

one_sided = scipy_stats.binomtest(win_count, trade_count, null_win_probability, alternative="greater")
two_sided = scipy_stats.binomtest(win_count, trade_count, null_win_probability, alternative="two-sided")
return {"p_one_sided": one_sided.pvalue, "p_two_sided": two_sided.pvalue}
One-sided form
p = Σk=1927 C(27, k) · (0.5)27 = 0.0261

Inputs actually used

win_count = 19, trade_count = 27, null_win_probability = 0.5. The 19 comes from (trades["pnl_pct"] > 0).sum() on the baseline log.

p one-sided0.0261alternative = greater
p two-sided0.0522reported for reference

Why one-sided is primary

The hypothesis is directional: the strategy is constructed to beat chance, not merely to differ from it in an unspecified direction. The two-sided value is reported alongside as the more conservative figure, and it sits just above 0.05 — which the paper states rather than omits.

This result does not survive costs

At the primary cost assumption of a 0.20% round trip, two trades — entered at candles 7938 and 8188, worth +0.12% and +0.13% gross — cross from winners into losers. The win rate falls to 62.96% and p rises from 0.0261 to 0.1239. Each cost scenario re-runs the binomial test in full on its own adjusted trade set rather than adjusting the gross p-value analytically. The honest overall answer is that the null is not rejected once realistic costs are charged.

Plain language — what a p-value of 0.0261 is saying

Imagine flipping a fair coin 27 times and counting heads. Most of the time you get somewhere near 13 or 14. Getting 19 or more is possible, just uncommon.

0.0261 is exactly how uncommon: about 26 times in every 1,000 attempts. So if the strategy genuinely had no edge, a run this good would still happen roughly once every 38 tries. That is unlikely enough to take seriously and nowhere near unlikely enough to be conclusive — especially on 27 trades.

The exact test is used rather than a normal approximation because 27 is small. The formula sums real binomial probabilities instead of assuming a bell curve, so no approximation error enters at a sample size where approximation error would matter.

2 · Percentile bootstrap confidence interval

bootstrap_resample() → run_bootstrap_ci()

How much sampling uncertainty surrounds the +30.31% total return figure?

The computation

values = np.asarray(values)
n = resample_size if resample_size is not None else len(values)     # 27
rng = np.random.default_rng(seed)                                   # seed = 42
resample_totals = np.empty(bootstrap_resamples)
resample_means  = np.empty(bootstrap_resamples)
for k in range(bootstrap_resamples):                                # B = 10,000
    sample = rng.choice(values, size=n, replace=True)
    resample_totals[k] = sample.sum()
    resample_means[k]  = sample.mean()

# then, in run_bootstrap_ci():
total_ci = np.percentile(resamples["resample_totals"], [2.5, 97.5])
mean_ci  = np.percentile(resamples["resample_means"],  [2.5, 97.5])

Four parameters carry the whole method: B = 10,000 repetitions, n = 27 draws each, with replacement, seed 42. The interval is the 2.5th and 97.5th percentiles of the 10,000 recorded totals.

Point estimate+30.3065%= the observed sum
95% CI, total+5.99 → +54.99percent
95% CI, average+0.22 → +2.04percent per trade
Resamples ≤ 00.75%99.25% positive

Design choices, each defensible by name

  • Why bootstrap at all. 27 trades is too few, and too skewed by a handful of large winners, to trust a normal-theory "mean ± 1.96 standard errors" interval. The bootstrap assumes nothing about distributional shape; it reuses the data's own shape.
  • Why with replacement. Drawing without replacement would just reshuffle the same 27 values and every resample total would be identical. Replacement is what lets a resample differ from the original at all.
  • Why exactly n = 27. Efron's prescription. Resampling at the original sample size makes the spread between resamples reflect genuine sampling uncertainty rather than an artifact of a changed sample size.
  • Why default_rng. The modern NumPy Generator API, not the legacy RandomState. With a fixed seed the 10,000 draws are byte-reproducible on any machine.
Disclosed simplification

This is the plain percentile bootstrap, not the bias-corrected and accelerated (BCa) variant, which adjusts the percentile cutoffs for skewness in the resampling distribution. The plain form is the standard textbook procedure. It is disclosed as a deliberate simplification rather than presented as the only option.

The two-interval disclosure

The dashboard computes the same bootstrap in TypeScript at B = 2,000 with its own mulberry32 PRNG, and lands on [+7.48%, +54.46%]. The cause was proven rather than assumed: mulberry32 was reimplemented in Python and run at B = 2,000, reproducing [+7.48%, +54.46%] exactly. The gap is the resample count alone — not a different method, seed, or trade set. Both are reported; they are not merged, because the dashboard's independence is what makes it a cross-check.

Plain language — what resampling actually simulates

You have 27 trade results and you want to know how much of the +30.31% was skill and how much was the particular order history happened to take. You cannot rerun 2022–2026. So you do the next best thing.

Put the 27 returns in a hat. Draw one, write it down, put it back, and repeat 27 times. You now have an alternative 27-trade history — some trades appearing twice, some not at all. Total it up. Do that 10,000 times and you have 10,000 plausible alternative outcomes.

Sort them, and the 250th and 9,750th values mark the middle 95%. That range is +5.99% to +54.99%. It is wide, which honestly reflects 27 trades. It excludes zero, and 99.25% of the alternative histories still made money.

3 & 4 · Pearson's r and Spearman's ρ

Do trades held longer tend to end up larger?

Both are called with x = trades["hold_bars"] and y = trades["pnl_pct"] across the same 27 baseline trades. Two thin wrappers around two SciPy calls; no custom math.

Pearson r+0.4907t = 2.82, df = 25

Why both

Pearson assumes a straight-line relationship and is sensitive to outliers — a concern here, since three trades carry 51.7% of total return. Spearman ranks the values first and asks only whether the relationship is consistently directional. They agree in sign and significance, so the association is not an artifact of a few extreme trades. That agreement is the point of reporting both.

A corrected reporting error

Two draft documents reported these p-values as p < 0.001. Independent recomputation gives 0.0094 and 0.0113 — still significant at α = 0.05 and α = 0.01, but the original claim overstated them by roughly a factor of ten and placed them in the wrong significance bucket. Both source documents were corrected. spearman_correlation() is also the one genuinely new function in the consolidated file: no earlier script in this repository computed Spearman's ρ, and it was added specifically so the already-published figure has committed code behind it.

Plain language — and the trap in this result

A correlation of +0.49 means the two quantities move together, moderately. Trades held longer did tend to earn more.

The trap: this is not advice to hold trades longer. The causation almost certainly runs the other way. A trade that is working keeps satisfying none of the exit conditions and so stays open; a trade that is failing hits its stop or its KDJ reset quickly and closes. Duration is largely an effect of the trade going well, not a cause. The correlation describes the exit ladder's behaviour, not a lever anyone could pull.

5 · Maximum drawdown

max_drawdown_pct(equity_curve)

What was the worst peak-to-trough fall this equity curve suffered along the way?

equity_curve = pd.Series(equity_curve)
running_max  = equity_curve.cummax()
drawdown_pct = (equity_curve - running_max) / running_max * 100
return drawdown_pct.min()
Formula
P(t) = maxu ≤ t E(u)     DD(t) = 100 · (E(t) − P(t)) / P(t)     MDD = mint DD(t)

Three lines, one subtlety: cummax() is the running peak, not the global maximum. Comparing against the global maximum would only measure the fall from the all-time high to the end, and would miss a deep decline that happened mid-window and later recovered.

Strategy−6.46%2.63% in market

Reported as a percentage rather than in dollars so three arms with very different equity-curve shapes can be compared directly from the same $10,000 start.

Plain language — why this is the number an investor feels

Total return tells you where you ended. Maximum drawdown tells you the worst moment along the way — how far your account fell from its own high-water mark before recovering.

Lump-sum buy-and-hold returned +90.07% over this window, but to collect it you had to sit through your account being worth 67% less than its peak. Most people sell before that. The strategy's −6.46% is not the product of better trading so much as of being out of the market almost all the time: it holds a position on only 2.63% of candles and cannot fall while it holds nothing.

6 · Sharpe and Sortino ratios

sharpe_sortino_ratios(bar_returns, periods_per_year)

How much return did this arm earn per unit of the risk it took?

mean_return = np.mean(bar_returns)
return_std  = np.std(bar_returns, ddof=1)
sharpe = (mean_return / return_std) * np.sqrt(periods_per_year) if return_std > 0 else float("nan")

downside_returns   = np.minimum(bar_returns, 0.0)
downside_deviation = np.sqrt(np.mean(np.asarray(downside_returns) ** 2))
sortino = (mean_return / downside_deviation) * np.sqrt(periods_per_year) if downside_deviation > 0 else float("nan")
Formulas
SR = ( R̄ / sR ) · √m    with sR the sample SD, ddof = 1
σd = √( (1/N) · Σ [min(R(t), 0)]² )     SoR = ( R̄ / σd ) · √m

The annualization factor

Two constants, each matched to its arm's own reporting frequency:

  • PERIODS_PER_YEAR_4H_BARS = 6 * 365.25 = 2,191.5 — for arms measured per 4-hour bar (strategy, lump-sum). The .25 is leap-year averaging.
  • PERIODS_PER_YEAR_WEEKLY = 52 — for arms measured at weekly contribution bars (DCA, blended sleeves).
Two disclosed assumptions — know these by name

Risk-free rate = 0. The textbook Sharpe ratio is E[R − Rf] / σ, where both numerator and denominator use excess return over a risk-free rate. This code uses raw per-bar returns, which is mathematically equivalent to setting Rf = 0. Defensible for a crypto strategy with no modelled cash leg, and every arm is treated identically so the ranking between arms is unaffected — but it is a real, nameable deviation from the general formula.

Minimum acceptable return = 0. Sortino & van der Meer's 1991 definition uses min(0, R − T) against a general target T. This code hardwires T = 0 via np.minimum(bar_returns, 0.0).

A shortcut this code correctly refuses

The downside deviation divides by N, the count of all periods — np.mean() over the full array, most of whose entries are zero. This follows the original 1991 definition. A widely circulated online tutorial divides instead by the count of losing periods only, which inflates the ratio. This code does not take that shortcut, which is worth being able to say if a panelist raises it.

The exposure caveat is not optional

The strategy's Sharpe of 1.114 exceeds buy-and-hold's 0.564 — but it holds a position on 2.63% of candles against 100% continuous exposure. Plain language — the two ratios and the √m

Sharpe divides average return by how much that return bounced around. Two strategies ending at the same place score differently if one got there smoothly and the other lurched.

Sortino makes one change: only downward moves count as risk. The reasoning is that nobody complains about an unexpectedly good day. This is why the strategy's Sortino (2.73) is so much higher than its Sharpe (1.11) — its variability is heavily skewed toward the upside.

The √m converts a per-period figure to an annual one. Returns scale with time but their standard deviation scales with the square root of time, so annualizing a ratio of the two multiplies by √m rather than m. For 4-hour bars m = 2,191.5, so the multiplier is about 46.8.

The contribution-netting formula — why injected capital is not counted as return
r(k) = ( V(k) − C(k) ) / V(k−1) − 1
V = portfolio value at contribution bar k, C = that week's own contribution

Without subtracting C(k), every weekly deposit would register as a gain and the DCA arm's Sharpe would be meaningless. The same formula governs the blended-sleeve model, so the two constructions cannot drift apart.

Net-of-cost variants: the strategy is charged 0.20% round trip subtracted from each trade's return; the two passive arms are charged 0.10% one-sided as a buy-price markup, since they buy and hold rather than round-tripping. The handoff's bootstrap subsection reads:

There is no difference. run_bootstrap_ci() sets the point estimate to the observed sum, on one line:

pnl_values  = trades_df["pnl_pct"].values
total_point = pnl_values.sum()          # ← this IS the observed sum
...
"total_return_point_pct": total_point,

Both figures are the same float, 30.306456356031937. One was rounded to four decimals (30.3065) and the other truncated (30.3064). The bootstrap distribution influences the interval, never the point estimate.

Why this one matters more than its size suggests

The sentence invites a question with no answer. A panelist who asks "why does your bootstrap point estimate differ from your trade sum?" is asking about a formatting artifact, and the only correct reply is that it does not differ — which reads as a retraction of a printed claim. Recommended fix: report one value at one precision, e.g. "the bootstrap's point estimate is the observed sum of the 27 trade returns, +30.3065%." No other number in the section changes.

F2 · A stale artifact carries prohibited statistics

Commit b9df7da removed the minimum-detectable-effect and power analysis from the code, and §18 prohibits MDE and power analysis from appearing anywhere in the paper "in any form." But artifacts/bootstrap_power_analysis.json, dated 2026-08-20 and still committed, contains a complete mde_power block: α, power, and per-criterion n_true / sd_true / observed_diff / mde / detectable entries for all five Order Block quality criteria.

The paper does not cite it. The file ships alongside the paper. Recommended: regenerate the artifact from the current code, or delete the mde_power key, before the repository is handed to anyone.

F3 · The canonical entrypoint prints the excluded ablation

§18 prohibits "any ablation, indicators-only arm, or component-isolation comparison, and any statistic computed from one." Running python research_analysis.py — the documented way to reproduce the paper — reaches step [3/10] and prints:

Arm 2 (flat-ATR stop): N=140 win_rate=47.14% total_return=-13.72%
  vs. locked N=140 win_rate=60.00% total_return=-14.63%  status=DIVERGE
Arm 3 (swing-pivot stop): N=138 win_rate=43.48% total_return=-23.85%
  vs. locked N=138 win_rate=55.07% total_return=-25.50%  status=DIVERGE

This is correct behaviour for the code. The script that produced the original ablation pools was never committed, so Section 4 is an honest reconstruction from the documented design, and it reports divergence loudly rather than reconciling it. The disclosure is exactly right.

The problem is placement: it is among the first things anyone reproducing the paper sees, it concerns a study the paper does not contain, and the word DIVERGE appears twice before any headline figure. The two locked ablation figures also still sit in the constants block as LOCKED_ABLATION_ARMS at line 158. Recommended: gate step 3 behind a flag, or add a README line saying what it is and why the paper excludes it.

F4 · The module docstring names two removed tests

Line 63, in the section map at the very top of the canonical file:

  5    Statistical test primitives (binomial/Fisher/Welch/bootstrap/etc.)

Both were removed by b9df7da and are confirmed absent from the source — a grep for fisher_exact, ttest_ind, f_oneway and kruskal returns nothing but this docstring line. Since §18 forbids Fisher's exact test and Welch's t-test from appearing "in any form, including as something considered and rejected," the first page of the file a reviewer opens naming both is worth ten seconds to fix.

F5 · Two buy-and-hold returns, one cited

The repository computes buy-and-hold twice, under two different and individually correct conventions:

run_benchmark_vs_passive()First bar's open$46,216.93+90.07%0.5642−67.21%

The paper cites +90.07%, which is correct — the handoff explicitly specifies the open-price convention for the lump-sum arm. But +87.65% is what the pipeline prints at step 5/10 and what artifacts/benchmark_dca_analysis.json stores, so anyone reproducing the run will see a buy-and-hold number that is not in the paper. Recommended: one line in Appendix A naming which function produced +90.07% and stating that the other figure is a different quantity, not a competing estimate of the same one.

F6 · A superseded doc describes tests that no longer exist

docs/research_statistics_reference.md is titled "Research Statistics Reference & Study Guide" and carries a superseded banner at the top. Below that banner it still documents one-way ANOVA and the Kruskal–Wallis H-test, complete with a worked ANOVA example — neither of which is among the six statistics in scope, and neither of which exists anywhere in the current code. Its threshold-sweep table is also flagged as not matching any disclosed value. The banner is easy to scroll past; the title is the one a judge would search for.

F7 · A one-bar caption imprecision

The handoff's Table 9 note describes the formulation window as "2018-01-01 to 2022-01-01." The code's actual window is 2018-01-01 08:00 → 2022-01-01 04:00 — it stops one 4-hour bar short so it never overlaps the main window's first bar at 2022-01-01 08:00. The behaviour is right and the row count the handoff states elsewhere (8,750) already reflects it; only the caption rounds.

Two things that are correct and might look otherwise

Already handled

The ATR comment. The code comment says Wilder's RMA; the code computes a plain rolling mean. The paper states the discrepancy explicitly and reports the rolling mean, which is what actually executes. Nothing to correct in the paper — only the comment is stale.

The default quality threshold. DEFAULT_MIN_OB_QUALITY = 1 yields 25 trades, and that is what artifacts/trades_default_view.csv contains. The paper's 27 requires min_ob_quality=0. Both are correct; anyone comparing a CSV against the paper needs to know which threshold the CSV was written at.

§ 12

Reproduce it

Three commands, no network, no credentials.

The full statistics pipeline

python research_analysis.py                      # offline; prints every figure in §10
python research_analysis.py --json-out out.json  # same run, machine-readable

Runs strictly against artifacts/candles.csv and artifacts/candles_extended.json. The only network call in the whole file — run_forward_oos_validation()'s live Binance pull — is gated behind --include-oos-live and off by default, so a bare run never touches the network. Ten steps, roughly a minute.

The regression harness

python scratch/regression.py

The golden master. Recomputes indicators and the OB-gated simulation from raw candles and compares against committed fixtures: per-bar indicator series to 1e-6, and all 27 trades matched on entry_idx to 1e-5. It names the first divergent trade rather than only failing. Run after every change; any diff means revert. Never regenerate the fixtures without asking first.

The dashboard

python research_analysis.py --serve --levels 0,1,2,3   # port 8765
python Run_All.py                                       # same, plus dependency install/build

Exports artifacts and database rows, then serves the TypeScript dashboard — the independent cross-check. Note --serve writes to artifacts/, and it does pull live candles (falling back to the local cache on failure), since producing a fresh snapshot is its purpose.
